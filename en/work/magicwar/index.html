Account and deck requests on the DB worker

Implementation flow

PacketManager copies request strings and card IDs into EnqueueSessionDB. Login, signup, profile queries, deck reads and replacement run on a single DBWorker queue, which also handles match-result persistence. The completion callback locks the session and checks its generation and closing state before updating it or sending a response.

Purpose

This removes synchronous DB waits from IOCP completion handling. The queue lock is held only while taking a task. Neither the queue lock nor the session lock is held during the database operation, allowing new requests and logout to proceed.

Alternatives and tradeoffs

One worker keeps FIFO execution and ownership of a single DB connection simple. At most 4096 tasks can wait in the queue; new work is rejected when it is full or stopping. Shutdown stops timers, marks sessions as closing, and waits for the DB worker before returning sessions to the pool.

Validation and remaining limits

Real table locks delayed login and profile/deck operations while Ping responsiveness was checked. Tests also verify that logout during a pending login does not leave the account reserved. A slow query still delays subsequent DB requests on this single worker. A write already in progress can commit after disconnect, but its response is not applied to the closed session.

Fragmented receives and accumulation bounds

Implementation flow

IOCP_Recv copies only as much received data as fits in the session buffer, then runs PacketParser to consume complete frames before continuing. No remaining space or an invalid length closes the connection. The complete frame limit is 4096 bytes, leaving 4088 bytes for the body after the 8-byte header.

Purpose

TCP does not preserve send boundaries. Incomplete frames must survive until the next receive, while coalesced frames must be consumed in order. Calculating remaining capacity before each copy prevents new bytes from overflowing an accumulated partial frame.

Alternatives and tradeoffs

A fixed limit simplifies memory use and bounds checks, but larger messages would need an explicit segmentation protocol. Invalid declared lengths close the connection instead of guessing where another header begins. Fixed-width signup and login fields are also checked for a terminator.

Validation and remaining limits

Socket tests cover split headers and bodies, a maximum-size frame followed by coalesced frames, oversized lengths and unterminated fields. These are targeted regressions, not proof that every I/O lifetime race or production load has been tested.

Separate SQL values from query text

Implementation flow

Account, profile and deck queries in UserManager use parameter markers. PreparedQuery binds strings and numeric values, copies result data and closes the statement. Signup inserts into several tables in a transaction and rolls back on failure.

Purpose

Quotes in an account ID or nickname are passed as values rather than concatenated into SQL. Keeping input separate from query text prevents the input from changing the meaning of a condition.

Alternatives and tradeoffs

Preparing a statement for each request is simple but has preparation overhead. The deployed schema still needs UNIQUE constraints on account IDs and nicknames. The synthetic test schema is not a production migration.

Validation and remaining limits

Tests cover signup, login and profile reads with quote/backslash-bearing IDs, plus an SQL-shaped ID treated as a literal value. This is not a penetration test of the entire authentication system.

A spell needs both content and runtime values

Implementation

MagicCaster looks up a local CardData prefab and server-fed CardRuntimeData before casting. It uses IFieldMagic to choose field placement or projectile launch, with an explicit meteor exception, and copies the relevant runtime values into the spawned spell.

Design rationale

Art/prefab identity and combat parameters change for different reasons. Separating them lets local content define appearance while runtime data supplies damage, speed, radius and duration. Initializing an instance with values also makes its behavior explicit when it is spawned.

Alternatives and the current tradeoff

Putting every value in the prefab minimizes lookups but duplicates balance data. One central switch for every spell keeps routing visible but grows with spell-specific behavior. The current design shares initialization through MagicProjectile and marks field behavior with an interface, while retaining some special cases.

Tradeoffs and verification

Card IDs, prefabs and runtime records must stay aligned. The meteor ID exception and required prefab components are coupling points to check when adding a spell.

Replacing a card is a request, not a local fact

Implementation

SettingSystem holds a pending card ID while the player selects an equipped slot. It sends the old and new card IDs, clears selection mode, and requests the equipped deck again only when the replacement response reports success.

Design rationale

The UI's intended change and the server's stored deck can differ when a request fails. Refreshing from the accepted state avoids treating a click as confirmation and reuses the same deck-to-UI path used on entry.

Alternatives and the current tradeoff

An optimistic local swap feels immediate but needs rollback. Returning the full updated deck in the replacement response would avoid a second round trip. The current requery is simpler to reuse but adds a request and a period of waiting.

Tradeoffs and verification

The current code identifies the previous card from its displayed sprite and logs replacement failures. Explicit slot IDs, a pending state and timeout handling would make the interaction less dependent on presentation state.

The October 2026 server update puts deck replacement and reads on the same DB worker queue. The existing response format and client requery after success are preserved. Integration tests verify replacement-before-read ordering.

DESIGN DECISION

The engineering problem

Multiplayer magic combat combines receive/send handling, reusable connection resources and database-backed game services. Those responsibilities should be readable as separate parts of the server.

The server uses IOCP workers, session/buffer/overlapped pools and a separate DB worker. My work includes magic/cooldown services, matches, profiles and ranks, with Unity-side game/network integration.
