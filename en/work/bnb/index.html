CSV transactions and room lifetime

A 32-client purchase test exposed a persistence failure: all four item categories wrote through the same temp.csv. Different requests could replace or remove one another’s temporary file. The follow-up change keeps CSV storage but commits a purchase’s balance and ownership together.

A unique temporary filename alone would leave lost updates and a balance/ownership split. A shared_ptr to a mutable Room alone would prevent deletion but not data races. The selected transaction boundary covers one logical account operation; room snapshots cover one consistent read. MOVE does not acquire the user persistence lock.

Room lookups now return immutable copies made under the room lock. Team changes and death registration mutate state only inside RoomManager. Death registration claims the result once per match, while the ready barrier clears match state before releasing its lock. A failed reward commit releases the claim for retry, checking the match generation. Broadcasts retain their recipients before releasing the room and client locks; queue insertion occurs after both locks are released.

The real server purchase test sends two requests per account, with 32 accounts split across character, balloon, emote and icon purchases. Correct persisted balance and ownership: 0/32 before, 32/32 after, in this reproduction. The unit harness also checks 96 concurrent profile/stat commits, 16 simultaneous purchase attempts, seven-file registration, precommit failure rollback and recovery after process termination between two replacements. The room test completes 12 matches while another room moves, checks one reward and one GAME_END per match, and churns 30 temporary rooms.

Reducing output-thread cost without losing slow-reader isolation

The first bounded-queue fix prevented a stalled reader from blocking other rooms, but created a writer thread for every connection. I replaced those writers with one shared IOCP output worker. Receive threads remain per connection.

At 64 connections, the median observed peak thread count fell from 132 to 69, and server CPU from 12.03% to 7.34% of one logical core. Median peak RSS fell from 16.03 to 14.49 MiB. The p95 median increased from 14.81 to 15.35 ms. This is a reduction in resource cost, not a claim that every response became faster.

In the separate stopped-reader test, one client in room A stops receiving. All probes stay inside healthy room B. Both the old bounded queue and the IOCP version delivered 300/300 B-room responses in each of three runs. Their p95 medians were 13.94 and 11.31 ms. A fixed pool of blocking send workers would limit thread count, but enough stalled peers could occupy every worker. Overlapped WSASend allows a slow socket to remain pending without tying up the completion worker. I selected one output worker for the measured range of 8–64 connections; these tests do not establish a production capacity limit or the optimal worker count.

Each connection keeps its own 256 KiB / 4,096-frame limit, including the in-flight batch. Only one operation is outstanding per connection, preserving order. A batch targets 16 KiB. Completions advance partial writes; the next batch returns to the shared completion queue to give other sockets a turn. The operation retains both its byte buffer and the connection until completion, including cancellation. Enqueue success means accepted for sending, not received by the peer.

Removing per-hit CSV reads

GetAttackByIndex reopened and parsed CharStat.csv for every HIT. The server now validates and loads the seven-entry attack table before accepting connections, then reads an immutable in-memory map. Unknown indices still return zero. Invalid startup data fails loading; changes to the file require a restart. This is a deliberate startup-snapshot policy, not hot reload or a database migration.

Actual UserManager code, 100,000 lookups, five alternating runs per variant, matching checksums. Warm filesystem cache; initial loading is excluded. Median elapsed time: 9044.14 ms → 0.2805 ms. This isolates file-open/parsing work versus a tiny hot map. It must not be presented as an equivalent speedup in the game or server throughput.

The Unity receiver also dispatched the incomplete final fragment returned by Split, and decoded UTF-8 separately for each TCP read. I added a 64 KiB bounded byte accumulator that dispatches only complete newline-delimited messages and decodes UTF-8 after framing. Tests cover fragmented/coalesced messages, split Korean/Japanese characters, exact size limits and malformed UTF-8. This is a correctness fix; no Unity FPS improvement was measured.

Validation: 7 output unit checks, 8 socket framing/room checks, 5 connection-lifecycle checks, and a real-socket HIT check delivering 28 expected damage responses without cross-room delivery. Startup-cache and standalone C# framing tests also passed. The 18 MOVE runs had no missing, duplicated, malformed or cross-room messages. End-to-end Unity gameplay and long-duration soak tests remain separate work.

The comparison uses the room-scoped revision as its baseline. Eight synthetic clients join two four-player waiting rooms. One reader in room 0 pauses reads with a requested 1,024-byte receive buffer. A peer offers 2,048-character chat payloads in bursts of 10 every 20 ms. After one second, room 1 sends 100 MOVE requests at 20 Hz, expecting 300 observer deliveries, followed by one second of drain. Quiet and stopped-reader conditions each run three times per revision, alternating order, on one Windows host over loopback.

I considered sending after releasing the shared lock, a dedicated writer per connection, and IOCP. Releasing the lock alone would not serialize concurrent writes to the same socket or bound pending data. I chose one writer with a bounded queue to preserve the existing text protocol and handlers while isolating socket waits. IOCP would reduce the per-connection thread cost, but requires a separate redesign of completion handling and buffer lifetime.

Handlers enqueue complete messages. Only SocketOutput::Run calls Winsock send. The writer combines available messages into batches targeted at 16 KiB and resumes from the returned byte count after a partial send. A single message larger than 16 KiB remains intact. FIFO order is preserved within the queue; concurrent producers are ordered by enqueue acquisition, not by a global game clock.

Pending payload is limited to 256 KiB and 4,096 frames per connection, including the batch currently being sent. Exceeding either limit disconnects that client. Waiting for space would reintroduce blocking under shared locks; dropping arbitrary messages would corrupt the meaning of chat, purchases and match events. These are experiment limits, not production-tuned capacity estimates. Deque overhead, a temporary batch copy, socket buffers and thread stacks are additional memory.

The partial-send loop, from the committed implementation

size_t offset = 0;
while (offset < batch.size() && !stopping_) {
    const int sent = sender_(socket_, batch.data() + offset, static_cast<int>(batch.size() - offset), 0);
    {
        std::lock_guard<std::mutex> lock(mutex_);
        ++stats_.sendCalls;
        if (sent > 0) stats_.sentBytes += sent;
    }
    if (sent <= 0) { Stop(2); break; }
    offset += sent;
}

Quiet-run latency did not materially improve. With eight connections, observed peak server threads increased from 12 to 20. The stalled baseline used little CPU because it was no longer processing the offered work; that is not an efficiency advantage. This patch retains thread-per-connection reception and adds one writer thread per connection.

QUIT now delegates cleanup to the receive loop, and SocketOutput owns shutdown, writer join and the final closesocket. Logout removes room membership before clearing identity. Lobby broadcasts copy recipient ownership and IDs under the client lock before building and enqueueing the message. Two room-deletion paths no longer call room-locked operations while holding the client lock.

Six deterministic tests exercise forced partial writes, four concurrent producers, byte and frame limits, batching and send failure. In the controlled batching test, 1,000 two-byte frames reached the injected sender in two calls, compared with 1,000 calls for a one-call-per-frame model. This counts sender invocations, not network packets, throughput or FPS. Thirteen real-socket regression checks cover the original eight framing/room cases plus invalid purchase numbers, logout/relogin, 20 QUIT/EOF cycles and four simultaneous disconnects. The churn checks returned to the initial thread count.

A reported hit becomes damage in the room

I implemented Arrow, Laser, Mace, Melody, Pitchfork, Spell and Sword behaviors, plus the WeaponSystem path for equipment, spawning and cooldowns. LocalPlayerController separates input sampling in Update from Rigidbody movement in FixedUpdate. Network attack data carries the selected weapon and transform; the laser path also supplies an obstacle-based distance.

A Unity weapon reports HIT with the weapon, attacker and target. ClientHandler checks team membership in cooperative mode, selects damage through GetAttackByIndex and delivers DAMAGE to the room. The receiving GameSystem applies that damage and updates the HUD. The server does not independently replay the collision.

I tried the room-leader approach while learning how rooms work and applying it to an actual game. In BalloonSystem, the room leader sends REMOVE_BALLOON when the timer expires; the server computes the water spread. Client collision reporting still forms part of the trust boundary. Moving collision and timing decisions to the server would require server-side world simulation and separate validation of prediction and correction.

The room boundary was not the delivery boundary

The original MOVE handler called BroadcastMessageExcept, which sent to every connected client except the sender. With 64 clients in 16 four-player rooms, each move could reach 63 clients although only three were intended recipients. This was a correctness bug as well as unnecessary work.

The October patch calls BroadcastToRoomExcept, checks the session nickname and finite coordinates, and buffers incoming TCP bytes until a complete newline-delimited message is available. A trailing partial message waits for the next recv. Lines over 4,096 bytes are rejected.

The first patch preserved the text protocol and Unity message format. A length-prefixed binary protocol would require coordinated client changes. It addressed framing and room delivery; the later bounded output patch is described above.

The baseline is 304b11b; the patched source is 737a92c. Both use the same fixture and build settings. The harness only changes the listening port and binds the test server to loopback. It creates synthetic accounts in an isolated directory.

CSV persistence and confirmed purchase feedback

I chose CSV because it was easy to start with before I had learned databases. I planned to replace it later but did not complete that migration. Account, profile, ownership and shop data therefore remain file-backed.

In my ShopUI change, BuyItem sends the request and disables the button without immediately setting selectedOwned to true. Returned item data refreshes the relevant tab only when that tab is selected. This avoids turning a click into confirmed ownership and keeps a response for one category from replacing another category’s visible content.

A user transaction holds the user-state lock from validation through mutation and commit. Writes build after-images in memory. A flushed redo journal is atomically published before replacing individual CSV files; startup replays an unfinished journal before accepting clients. A failed precommit write rolls memory back. Failure after the journal commit point stops the process with the journal retained for recovery. A directory lease rejects a second server process using the same data directory.

A unique temporary filename alone would leave lost updates and a balance/ownership split. A shared_ptr to a mutable Room alone would prevent deletion but not data races. The selected transaction boundary covers one logical account operation; room snapshots cover one consistent read. MOVE does not acquire the user persistence lock.

What I would test next

The user-state mutex serializes account writes, and each transaction snapshots the user vectors and rewrites affected CSVs. This favors correctness and compatibility over high write throughput. These tests do not establish database-scale capacity, recovery from disk corruption, or match restoration after a server restart. Client-reported hits still need independent server validation. Full process shutdown and Unity allocation profiling remain separate work.

From implementation to a pricing question

Deciding prices for this game motivated my separate CNN consumption-pattern simulation. I presented the research at I2P-CON, then refined it for the CISC-W 2025 poster. The CNN study is not deployed inference in this game server.
