동시 구매 저장과 방 객체 수명 수정

32개 클라이언트의 동시 구매에서 저장 충돌을 재현했습니다. 네 종류의 아이템 저장 함수가 모두 temp.csv를 사용해 다른 요청의 임시 파일을 덮어쓰거나 삭제했습니다. 기존 CSV 형식을 유지하면서 재화 차감과 보유 목록을 한 번의 구매 단위로 저장하도록 고쳤습니다.

임시 파일명만 바꾸면 동시 변경 유실과 재화, 보유 목록의 불일치가 남습니다. 방을 shared_ptr로만 바꾸어도 삭제 이후 접근은 막을 수 있지만 동시 변경은 보호하지 못합니다. 구매는 하나의 트랜잭션으로 묶고, 방 조회는 일관된 복사본을 읽는 방식으로 정리했습니다. MOVE 처리는 사용자 저장 잠금을 거치지 않습니다.

방 조회는 잠금 안에서 만든 읽기 전용 복사본을 반환합니다. 팀 변경과 사망 처리는 RoomManager 안에서 잠금을 잡고 수행하며, 경기별 승패 확정은 한 번만 허용합니다. 복귀 준비가 끝나면 같은 잠금 안에서 경기 상태를 정리합니다. 보상 저장에 실패하면 경기 번호를 확인한 뒤 재시도할 수 있도록 승패 확정을 되돌립니다. 방송은 수신자의 소유권을 확보한 뒤 방과 접속자 잠금을 풀고 송신 큐에 넣습니다.

실제 서버에 32개 계정으로 접속해 캐릭터, 물풍선, 감정 표현, 아이콘 구매를 동시에 요청하고 계정마다 같은 요청을 두 번 보냈습니다. 저장된 잔액과 보유 목록이 모두 맞은 계정은 이 재현에서 수정 전 0/32, 수정 후 32/32였습니다. 별도로 프로필과 전적 저장 96건, 동시 구매 시도 16건, 가입 시 파일 7개 저장, 기록 확정 전 실패 시 복원, 파일 두 개 중 하나를 교체한 직후 종료한 상태의 복구를 검사했습니다. 방 검사는 다른 방의 이동과 경기 종료 12회를 겹치고, 경기마다 보상과 GAME_END가 한 번인지 확인한 뒤 임시 방 30개를 생성하고 삭제합니다.

같은 조건에서 지연 재측정

p95 중앙값은 세 조건 모두 늘었습니다. 64개 연결에서는 CPU 중앙값이 9.22%에서 7.65%로 줄었고, 8개와 32개에서는 늘었습니다. 스레드는 13, 37, 69개로 같았습니다. 기대한 전달 624,000건은 모두 도착했고 다른 방 전달과 중복은 없었습니다. 저장과 방 상태의 오류를 고친 결과이며, 전반적인 지연 개선을 입증한 결과는 아닙니다.

같은 Windows 장비와 MOVE 전달 하네스, Release x64에서 방당 4명, 클라이언트당 초당 20회를 보냈습니다. 각 연결 수에서 버전별 5회, 준비 2초, 측정 10초, 수신 대기 2초를 적용하고 버전 순서를 번갈아 실행했습니다. 지연은 송신 직전부터 관찰자가 완성된 줄을 받을 때까지이며 측정 클라이언트의 이벤트 루프 대기도 포함합니다. CPU 100%는 논리 코어 하나입니다. Unity 렌더링과 전투 시뮬레이션을 제외한 대기실 전달 경로입니다.

느린 수신자 격리를 유지하면서 송신 스레드 비용 줄이기

첫 송신 큐 수정은 느린 수신자가 다른 방을 멈추는 문제를 막았지만, 연결마다 송신 스레드를 하나씩 만들었습니다. 이 송신 스레드를 공용 IOCP 워커 하나로 교체했습니다. 수신 스레드는 여전히 연결마다 하나입니다.

64개 연결에서 관찰한 최대 스레드 수의 중앙값은 132개에서 69개, 서버 CPU는 논리 코어 하나 기준 12.03%에서 7.34%로 줄었습니다. 최대 RSS의 중앙값은 16.03 MiB에서 14.49 MiB로 줄었습니다. 반면 p95 중앙값은 14.81 ms에서 15.35 ms로 늘었습니다. 자원 비용은 줄었지만 모든 응답이 빨라졌다는 결과는 아닙니다.

같은 Windows 장비, Release x64, TCP 루프백에서 방마다 4명, 클라이언트마다 초당 MOVE 20회를 보냈습니다. 연결 수와 버전별로 3회 반복하고 준비 2초, 측정 10초, 수신 대기 2초를 적용했습니다. 버전 실행 순서는 번갈아 배치했습니다. 아래 값은 회차별 값의 중앙값이며 p95도 회차별 p95의 중앙값입니다. CPU 100%는 논리 코어 하나입니다. 참가자가 있는 대기실의 전달 경로를 측정했으며 Unity 렌더링, 인터넷 통신, 전체 전투 시뮬레이션은 포함하지 않습니다.

별도 읽기 중단 실험에서는 A방의 한 클라이언트가 수신을 멈춥니다. 확인용 요청과 응답은 정상 B방 안에서만 오갑니다. 기존 제한 큐와 IOCP 버전 모두 3회 각각 B방 응답 300/300건을 전달했습니다. p95 중앙값은 13.94 ms와 11.31 ms였습니다. 아래의 0/300 → 300/300 그래프는 앞선 blocking send 수정의 기록이며 이번 IOCP 비교 결과와 구분됩니다.

blocking send를 고정 크기 스레드 풀에 넣으면 스레드 수는 제한할 수 있지만, 느린 수신자가 모든 워커를 점유할 수 있습니다. overlapped WSASend는 느린 소켓의 송신을 대기 상태로 두면서 완료 워커를 반환합니다. 이번에 측정한 8~64개 연결 범위에는 송신 워커 하나를 적용했습니다. 이 실험으로 운영 환경의 최대 동접이나 최적 워커 수를 확정하지는 않았습니다.

연결마다 전송 중인 묶음을 포함해 256 KiB와 4,096개 메시지 한도를 유지합니다. 연결별로 진행 중인 송신을 하나만 두어 순서를 보존하고, 16 KiB를 기준으로 메시지를 묶습니다. 부분 완료는 남은 바이트부터 이어 보냅니다. 다음 묶음은 공용 완료 큐에 다시 넣어 다른 연결에도 처리 기회를 줍니다. 취소된 경우에도 완료 통지를 받을 때까지 작업 객체가 버퍼와 연결의 수명을 유지합니다. 큐 삽입 성공은 상대의 수신 완료를 의미하지 않습니다.

피격 처리마다 반복하던 CSV 읽기 제거

GetAttackByIndex는 HIT마다 CharStat.csv를 열고 파싱했습니다. 서버가 연결을 받기 전에 공격력 7개를 검증해 읽고, 이후에는 변경하지 않는 메모리 맵을 조회하도록 바꿨습니다. 없는 인덱스는 기존처럼 0을 반환합니다. 시작 데이터가 잘못되면 로딩에 실패하며, 파일 변경은 서버를 다시 시작해야 반영됩니다. 시작 시점의 설정을 유지하는 정책이며 핫 리로드나 DB 전환은 아닙니다.

실제 UserManager 코드에서 조회 10만 회를 버전별 5회씩 번갈아 실행했고 결과 체크섬은 모두 같았습니다. 파일 캐시가 준비된 조건이며 초기 로딩은 제외했습니다. 소요 시간 중앙값은 9044.14 ms → 0.2805 ms였습니다. 반복적인 파일 열기와 파싱을 작은 메모리 맵 조회와 비교한 결과입니다. 게임 전체나 서버 처리량이 같은 비율로 빨라졌다고 해석할 수 없습니다.

Unity 수신부는 Split 결과의 마지막 미완성 조각까지 처리하고, TCP 수신 조각마다 UTF-8을 따로 디코딩하고 있었습니다. 64 KiB 상한의 바이트 누적 버퍼를 넣어 개행으로 완성된 메시지만 처리하고 그 뒤에 UTF-8을 해석하도록 바꿨습니다. 분할 수신, 여러 메시지의 합쳐진 수신, 한글과 일본어 바이트 분할, 크기 경계와 잘못된 UTF-8을 검사했습니다. 정확성 수정이며 Unity FPS 개선 수치를 측정한 것은 아닙니다.

송신 단위 검사 7개, 실제 소켓의 수신 경계와 방 구분 검사 8개, 연결 정리 검사 5개를 통과했습니다. 실제 HIT 경로에서도 기대한 피해 응답 28건과 다른 방 전달 0건을 확인했습니다. 시작 공격력 캐시와 독립 C# 수신 파서 검사도 통과했습니다. MOVE 18회 측정에서 누락, 중복, 형식 오류, 다른 방 전달은 없었습니다. Unity 전체 플레이와 장시간 부하는 별도의 검증이 필요합니다.

CSV 저장과 방 수명은 이후 상태 일관성 수정에서 다뤘습니다. 위 IOCP 수치는 당시 3회 측정 기록입니다.

이전 단계의 기록입니다. 당시에는 연결마다 blocking 송신 스레드를 두었습니다. 현재 구현은 위의 IOCP 방식이며 이전 측정값은 변경 이력으로 보존합니다.

MOVE 전달 범위를 고친 뒤에도 문제가 남았습니다. 읽기를 멈춘 클라이언트 때문에 send가 막히면 방 잠금이 풀리지 않아 다른 방의 요청까지 진행하지 못했습니다. 실제 소켓으로 재현한 뒤, 연결마다 크기를 제한한 송신 큐를 두고 소켓 쓰기를 분리했습니다.

읽기 중단 조건에서 기존 코드는 3회 모두 다른 방의 응답 300건 중 0건을 관찰 시간 내에 전달했습니다. 수정 후에는 매번 300건 전부 전달했고 중복은 없었습니다. 느린 연결의 영향을 분리한 결과입니다. 인터넷 지연이나 최대 동접 수를 측정한 결과는 아닙니다. 기존 코드에서는 받은 응답이 없어 p95를 계산할 수 없으며, 이를 0ms로 적거나 배속 향상률을 계산하지 않았습니다.

비교 기준은 이미 방별 MOVE 전달을 적용한 버전입니다. 가상 클라이언트 8명이 4인 대기실 두 개에 접속합니다. 0번 방의 한 수신자는 수신 버퍼를 1,024바이트로 요청하고 읽기를 멈춥니다. 같은 방의 다른 클라이언트는 2,048자 채팅을 20ms마다 10개씩 보냅니다. 1초 뒤 다른 방에서 MOVE 100건을 20Hz로 보내 관찰자 응답 300건을 기다리고, 마지막 1초를 추가 수신 시간으로 둡니다. 정상 조건과 읽기 중단 조건을 버전별 3회씩 번갈아 실행했습니다. 서버와 생성기는 같은 Windows PC의 loopback에서 실행했습니다.

공유 잠금을 풀고 송신하는 방법, 연결별 송신 스레드, IOCP를 비교했습니다. 잠금만 풀면 같은 소켓에 여러 스레드가 동시에 쓰는 문제와 송신 대기량 문제가 남습니다. 기존 텍스트 프로토콜과 핸들러를 유지하면서 소켓 대기를 분리하기 위해 연결별 단일 writer와 제한된 큐를 선택했습니다. IOCP는 연결당 스레드 비용을 줄일 수 있지만 완료 통지와 버퍼 수명 관리부터 별도로 바꿔야 합니다.

핸들러는 완성된 메시지를 큐에 넣고, 실제 Winsock send는 SocketOutput::Run만 호출합니다. 대기 중인 메시지는 16 KiB를 기준으로 묶습니다. 일부만 전송되면 반환된 바이트 수만큼 위치를 옮겨 나머지를 이어 보냅니다. 단일 메시지가 16 KiB보다 크면 그 메시지는 그대로 처리합니다. 큐의 순서는 유지하며, 동시 생산자 사이의 순서는 게임 전체 시간이 아닌 큐 잠금 획득 순서입니다.

연결 하나의 대기 payload를 256 KiB와 4,096개 메시지로 제한했습니다. 전송 중인 묶음도 포함합니다. 한도를 넘으면 해당 연결을 종료합니다. 빈자리가 날 때까지 기다리면 공유 잠금 안에서 다시 막히고, 메시지를 임의로 버리면 채팅과 구매, 경기 이벤트의 의미가 깨질 수 있기 때문입니다. 이 한도는 실험값이며 운영 환경에서 조정한 용량은 아닙니다. deque 관리 비용, 임시 묶음 복사, 소켓 버퍼와 스레드 스택은 별도 메모리입니다.

다음에 확인할 문제

계정 쓰기는 하나의 사용자 잠금으로 직렬화하며, 트랜잭션마다 사용자 벡터를 복사하고 변경한 CSV를 다시 씁니다. 기존 형식과 저장 일관성을 유지하는 선택이며 높은 쓰기 처리량을 입증한 결과는 없습니다. 디스크 손상 복구와 재시작 후 진행 중 경기 복원도 검증 범위에 포함되지 않습니다. 클라이언트가 보고하는 명중의 서버 검증, 서버 전체 종료, Unity 할당량 측정은 남아 있습니다.

구현에서 가격정책 연구로

이 게임의 아이템 가격을 고민하면서 별도의 CNN 소비 패턴 시뮬레이션 연구를 진행했습니다. I2P-CON에서 발표한 뒤 보완해 CISC-W 2025 포스터로 발표했습니다. CNN 추론을 이 게임 서버에 배포한 것은 아닙니다.
