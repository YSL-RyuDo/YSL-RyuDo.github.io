계정과 덱 요청을 DB 워커에서 처리

로그인과 프로필·덱 요청 각각에 실제 MariaDB 잠금을 걸었습니다. 잠금 중 Ping 응답과 로그아웃 종료를 확인했고, 잠금 해제 후 프로필→덱 응답 순서를 확인했습니다. 27개 회귀 검사를 통과한 로컬 실행이며, 그래프의 시간은 이 한 번의 측정값입니다.

  1. 01IOCP에서 요청을 해석
  2. 02제한된 큐 → 단일 DB 워커
  3. 03세션 세대를 확인하고 응답

IOCP 완료 처리에서 동기 DB 호출을 기다리지 않도록 실행 경로를 분리했습니다. 큐 잠금은 작업을 꺼낼 때만 유지합니다. DB 실행 동안에는 큐 잠금과 세션 잠금을 잡지 않아 다음 요청과 로그아웃을 처리할 수 있습니다.

구현 흐름·대안·검증 범위와 코드 근거

구현 흐름

PacketManager는 요청 문자열과 카드 ID를 복사해 EnqueueSessionDB에 전달합니다. 로그인, 회원가입, 프로필 조회, 덱 조회와 교체는 단일 DBWorker의 큐에서 실행합니다. 경기 결과 저장도 이 워커를 사용합니다. 완료 콜백은 세션 잠금을 잡고 generation과 closing을 확인한 뒤 상태를 갱신하거나 응답을 보냅니다.

이 구조의 목적

IOCP 완료 처리에서 동기 DB 호출을 기다리지 않도록 실행 경로를 분리했습니다. 큐 잠금은 작업을 꺼낼 때만 유지합니다. DB 실행 동안에는 큐 잠금과 세션 잠금을 잡지 않아 다음 요청과 로그아웃을 처리할 수 있습니다.

대안과 현재 구현의 절충

작업자 하나는 요청의 FIFO 순서와 단일 DB 연결 사용을 단순하게 만듭니다. 대기 작업은 최대 4096개이며, 큐가 가득 차거나 종료가 시작된 뒤에는 신규 작업을 거절합니다. 서버는 타이머를 중단하고 세션을 종료 상태로 바꾼 뒤 DB 워커를 기다리므로 세션을 먼저 반환하지 않습니다.

검증 범위와 남은 한계

실제 DB 테이블 잠금으로 로그인과 프로필 및 덱 작업을 지연시킨 상태에서도 Ping이 응답하는지 확인했습니다. 작업 중 로그아웃한 계정이 나중에 로그인 상태로 남지 않는지도 검사했습니다. 단일 워커는 느린 쿼리 뒤의 DB 요청까지 지연시키며, 이미 시작된 쓰기는 연결이 끊겨도 완료될 수 있습니다. 종료된 세션에는 그 응답을 적용하지 않습니다.

구현 흐름·대안·검증 범위와 코드 근거

구현 흐름

IOCP_Recv는 수신 데이터를 세션 버퍼의 남은 공간만큼 나눠 복사하고, 매번 PacketParser를 실행해 완성 프레임을 소비합니다. 남은 공간이 없는 상태나 잘못된 길이는 연결 종료로 처리합니다. 8바이트 헤더와 본문을 합친 상한은 4096바이트이므로 본문 상한은 4088바이트입니다.

이 구조의 목적

TCP는 송신 단위의 경계를 보존하지 않습니다. 미완성 프레임은 다음 수신까지 남겨 두고, 여러 프레임이 한 번에 들어오면 순서대로 처리해야 합니다. 복사 전에 남은 용량을 계산하면 미완성 데이터 뒤에 새 수신을 붙일 때 버퍼를 넘는 경로를 막을 수 있습니다.

대안과 현재 구현의 절충

고정된 상한은 메모리 사용과 경계 검사를 단순하게 하지만 큰 메시지는 별도의 분할 규약이 필요합니다. 선언된 길이가 잘못된 연결은 임의로 다음 헤더를 추측하지 않고 종료합니다. 로그인과 회원가입의 고정 길이 문자열에는 종료 문자도 검사합니다.

검증 범위와 남은 한계

헤더와 본문을 나눠 전송하는 경우, 최대 크기 프레임 뒤에 여러 프레임을 붙인 경우, 상한 초과 길이와 종료 문자가 없는 입력을 실제 소켓으로 검사했습니다. 이 결과는 해당 회귀 사례에 대한 확인이며 모든 I/O 수명 경합이나 운영 부하를 검증한 결과는 아닙니다.

구현 흐름

UserManager의 계정, 프로필과 덱 쿼리는 값 자리에 매개변수를 사용합니다. PreparedQuery가 문자열과 숫자를 바인딩하고, 결과를 복사한 뒤 statement를 닫습니다. 회원가입의 여러 테이블 삽입은 트랜잭션 안에서 처리하고 실패하면 롤백합니다.

이 구조의 목적

계정 ID나 닉네임에 따옴표가 들어가도 SQL 구문으로 연결하지 않고 값으로 전달합니다. 쿼리 문장과 사용자 입력을 분리해 입력 때문에 조건식의 의미가 바뀌는 경로를 없앱니다.

대안과 현재 구현의 절충

매 요청마다 statement를 준비하는 방식은 단순하지만 준비 비용이 있습니다. 실제 DB의 ID와 닉네임 UNIQUE 제약은 유지해야 합니다. 테스트 스키마는 합성 데이터를 위한 것이며 배포 DB를 바꾸는 마이그레이션은 아닙니다.

검증 범위와 남은 한계

따옴표와 역슬래시를 포함한 계정 생성, 로그인과 프로필 조회를 검사했습니다. SQL 조건식처럼 보이는 ID가 일반 문자열로 취급되는지도 확인했습니다. 인증 전체에 대한 침투 시험을 수행했다는 뜻은 아닙니다.

구현 흐름

MagicCaster는 시전 전에 로컬 CardData의 프리팹과 서버에서 받은 CardRuntimeData를 확인합니다. IFieldMagic 여부로 장판 배치와 투사체 발사를 나누되 운석은 별도 예외로 처리하고, 생성한 마법에 필요한 런타임 수치를 복사합니다.

이 구조가 필요한 이유

프리팹과 그래픽을 바꾸는 이유와 전투 수치를 바꾸는 이유는 다릅니다. 둘을 나누면 로컬 콘텐츠가 외형을 담당하고 런타임 데이터가 공격력과 속도, 반경과 지속 시간을 공급할 수 있습니다. 생성 시점에 값을 넘기므로 해당 마법이 어떤 수치로 시작했는지도 명확해집니다.

대안과 현재 구현의 절충

모든 수치를 프리팹에 넣으면 조회는 적지만 밸런스 데이터가 중복될 수 있습니다. 모든 마법을 하나의 switch에서 처리하면 분기는 한눈에 보이지만 개별 동작이 늘수록 커집니다. 현재는 MagicProjectile의 초기화를 공유하고 인터페이스로 장판을 구분하되 일부 예외는 남겨 둔 구조입니다.

장단점과 검증 범위

카드 ID와 프리팹, 런타임 레코드가 서로 맞아야 합니다. 마법을 추가할 때 운석 ID 예외와 프리팹의 필수 컴포넌트를 함께 확인해야 합니다.

구현 흐름

SettingSystem은 슬롯을 고르는 동안 교체할 카드 ID를 임시로 보관합니다. 이전 카드와 새 카드 ID를 전송한 뒤 선택 모드를 끝내고, 교체 성공 응답을 받았을 때 장착 덱을 다시 요청합니다.

이 구조가 필요한 이유

요청이 실패하면 화면에서 바꾸려던 내용과 서버에 저장된 덱이 달라집니다. 승인된 상태를 다시 읽으면 클릭을 확정으로 취급하지 않고, 화면 진입 때 사용하는 덱 표시 경로도 재사용할 수 있습니다.

대안과 현재 구현의 절충

로컬에서 먼저 바꾸면 즉각 반응하지만 실패 시 되돌리는 처리가 필요합니다. 교체 응답에 새 덱 전체를 담으면 추가 왕복을 줄일 수 있습니다. 현재의 재조회는 기존 경로를 재사용하기 쉽지만 요청과 대기 시간이 추가됩니다.

장단점과 검증 범위

현재 코드는 표시된 스프라이트에서 이전 카드를 찾고 교체 실패를 로그로 남깁니다. 명시적인 슬롯 ID와 처리 중 상태, 시간 초과 처리를 추가하면 화면 표시와 요청 처리를 더 명확하게 분리할 수 있습니다.

2026년 10월 서버 보완에서 덱 교체와 덱 조회를 같은 DB 워커 큐에 넣었습니다. 교체 성공 뒤 클라이언트가 덱을 재조회하는 응답 형식은 유지했습니다. 교체 후 조회가 순서를 지키는지 통합 검사로 확인했습니다.
